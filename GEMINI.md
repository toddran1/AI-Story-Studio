# AI Story Studio --- Gemini Coding Instructions

These instructions apply to all coding work in this repository.

The goal is to make correct, maintainable, surgical changes while
preserving the architecture and avoiding duplicate or layered
implementations.

## 1. Read Before Editing

Before modifying an existing function, class, module, component, route,
helper, schema, or test:

1.  Read the complete relevant implementation.
2.  Understand its imports, control flow, early returns, helpers, and
    callers.
3.  Search the repository for related implementations.
4.  Determine whether the requested change replaces existing behavior,
    extends existing behavior, or introduces genuinely new behavior.
5.  Only then make the change.

Do not patch a file based only on a search-result snippet or a few
surrounding lines. Understand the existing implementation before
modifying it.

## 2. Replace --- Do Not Layer

When new behavior is intended to replace existing behavior, **REMOVE OR
REWRITE THE OLD IMPLEMENTATION.**

Do not append the new implementation beside the old implementation.

Incorrect:

``` ts
const result = oldImplementation();
const result = newImplementation();
```

Correct:

``` ts
const result = newImplementation();
```

Incorrect:

``` ts
return oldImplementation();
return newImplementation();
```

Correct:

``` ts
return newImplementation();
```

Do not preserve obsolete behavior "just in case." If backward
compatibility genuinely requires two paths, implement that deliberately
and document why both exist.

## 3. Duplicate Code Is a Correctness Bug

Duplicate code introduced during an edit is considered a failed
implementation.

Before completing any task, inspect every modified file for:

-   duplicate imports
-   duplicate variable declarations
-   duplicate constants
-   duplicate function declarations
-   duplicate methods
-   duplicate types or interfaces
-   duplicate React components
-   duplicate JSX controls
-   duplicate event handlers
-   duplicate CSS selectors
-   duplicate API routes
-   duplicate switch cases
-   duplicate condition blocks
-   duplicate tests
-   duplicated error handling
-   duplicated warning collection
-   old implementation followed by new implementation
-   unreachable legacy code after `return`, `throw`, `continue`, or
    `break`
-   obsolete fallback behavior
-   unused helpers left behind by refactoring

The final source file should contain one coherent implementation of the
requested behavior.

## 4. Search Before Creating

Before creating any new helper, service, utility, type, interface,
schema, React component, hook, CSS class, API route, endpoint, provider,
validator, filesystem helper, or artifact-state helper, search the
repository for an existing implementation with the same or similar
responsibility.

If one already exists, prefer reusing it, extending it, or refactoring
it instead of creating a parallel abstraction.

Do not create multiple sources of truth for the same concept.

## 5. Preserve Existing Architecture

AI Story Studio has centralized systems for important concepts. Use the
existing architecture instead of recreating its logic locally.

Examples include stage execution planning, artifact availability and
freshness, stale propagation, pipeline dependency handling, provider
routing, model routing, Story Bible canonical identity, entity
localization, pronunciation, Visual Canon, Scene Studio, QA lifecycle
and freshness, production planning, job execution, filesystem/storage
helpers, and fingerprint/provenance handling.

If a centralized helper exists, use it. Do not recreate the same
semantics independently inside individual services, routes, components,
or pages.

## 6. Stale Artifact Semantics

Maintain the distinction between:

``` text
Availability:
  available
  missing
  invalid

Freshness:
  current
  stale

Production reusability:
  separate decision
```

The intended behavior is:

``` text
Valid + Current → usable → may be reusable
Valid + Stale → usable → warn the user → may be regenerated by full production policy
Missing → unavailable → block or rebuild when required
Invalid → unavailable → block or rebuild
```

**Stale does not mean missing. Stale does not mean invalid. Stale does
not mean unusable.**

Do not solve stale-data problems by clearing stale flags, silently
marking prerequisites current, automatically regenerating prerequisites,
treating stale artifacts as missing, or hiding stale artifacts from the
user.

Consuming a stale artifact must not silently make that artifact current.

## 7. Preserve Pipeline Direction and Provenance

Artifacts must not silently travel backward through the dependency
graph.

``` text
Narration
    ↓
Raw TTS
    ↓
Mastered Audio
```

Mastered Audio must never be copied into Raw TTS simply because Raw TTS
is missing.

A downstream artifact must not masquerade as an upstream source
artifact.

Preserve artifact provenance, fingerprints, dependency relationships,
provider/model provenance, approval state, and freshness state.

Do not fabricate missing provenance or metadata merely to make an
operation succeed.

## 8. Do Not Confuse Availability, Freshness, Completion, or Approval

Before changing a status check such as `status === "complete"`,
determine what the check actually means.

It may represent artifact availability, artifact freshness, stage
completion, production reusability, approval, workflow readiness, or
artifact integrity. These are not interchangeable.

Do not globally replace status checks without understanding their
purpose.

Approved + Stale artwork can still be usable. Approved + Missing artwork
is an integrity problem. Stale mastered audio can still be consumed
downstream. Missing raw TTS can still prevent rerunning Audio Mastering.

## 9. Prefer Surgical Changes

Make the smallest coherent change that correctly solves the requested
problem.

Avoid unrelated cleanup unless required for correctness. Do not rewrite
an entire module for a small bug, rename unrelated symbols, reformat
entire files unnecessarily, redesign unrelated architecture, change
unrelated UI, alter unrelated behavior, or introduce new abstractions
without need.

Keep diffs focused and reviewable.

## 10. Preserve Existing Behavior Unless Intentionally Changed

Before changing an existing behavior, determine whether the task
actually requires that behavior to change.

Do not accidentally remove error handling, retries, rollback behavior,
stale warnings, approval checks, integrity checks, provenance, manual
overrides, user decisions, or existing compatibility behavior.

If behavior must change, make the change explicit and add regression
coverage when practical.

## 11. Error Handling

Do not hide real integrity or processing failures by silently falling
back.

Distinguish meaningful error categories where possible:

``` text
missing prerequisite
invalid/corrupt artifact
metadata/integrity mismatch
stale but usable
approval required
provider failure
processor failure
configuration failure
```

A fallback should only occur when fallback behavior is intentionally
supported.

Do not turn `artifact expected but corrupt` into
`artifact absent, use fallback` unless that behavior is explicitly part
of the product design.

User-facing errors should be actionable. Do not expose credentials,
secrets, tokens, unsafe environment information, or unnecessary
filesystem details.

## 12. Tests Are Product Requirements

Do not weaken, delete, skip, or rewrite an existing regression test
simply to make a new implementation pass.

When a test fails:

1.  understand why it failed;
2.  determine whether the implementation or expectation is wrong;
3.  fix the implementation when the existing behavior remains required.

If product behavior intentionally changes, update the test deliberately
and explain why its previous expectation is obsolete.

For bug fixes, add regression coverage when practical. Tests should
verify observable behavior rather than unnecessarily coupling to
implementation details.

## 13. No Validation Bypasses

Do not use the following merely to make code compile or tests pass:

``` text
any
@ts-ignore
@ts-expect-error
eslint-disable
disabled tests
skipped tests
empty catch blocks
fake success responses
hard-coded test-only production behavior
```

These mechanisms may only be used when there is a legitimate, documented
reason. Fix the underlying implementation whenever possible.

## 14. Mandatory Post-Edit File Review

After editing code, perform a second pass before considering the
implementation finished.

For **every modified file**:

1.  Read the resulting file as a whole or the complete relevant
    sections.
2.  Do not review only the patch that was applied.
3.  Check imports.
4.  Check declarations.
5.  Check control flow.
6.  Check early returns.
7.  Check error paths.
8.  Check existing helpers.
9.  Check the old implementation was actually removed.
10. Check the new implementation is reached by real execution paths.

Specifically search for duplicate imports, duplicate declarations,
old/new implementations existing simultaneously, unreachable code, dead
branches, obsolete fallbacks, unused imports, unused helpers, temporary
debugging code, and accidental test duplication.

This review is mandatory.

## 15. Mandatory Final Diff Audit

Before reporting a coding task complete, inspect the final Git diff.

Ask:

``` text
Did I append when I should have replaced?
Is the old implementation still present?
Did I introduce duplicate imports?
Did I introduce duplicate declarations?
Are there two implementations of the same behavior?
Is any new code unreachable?
Did I leave an obsolete fallback?
Did I create a second abstraction for an existing concept?
Did I weaken an existing test?
Did I accidentally modify unrelated files?
Did I leave debugging or temporary code?
Does every changed line have a reason to exist?
```

If any answer reveals a problem, fix it before completion. Do not rely
solely on tests to detect these problems.

## 16. TypeScript Is a Required Quality Gate

Run TypeScript validation after implementation. Compilation errors must
be resolved before completion.

Pay particular attention to duplicate identifiers, duplicate
declarations, duplicate imports, unreachable code, unused imports,
incorrect signatures, incompatible types, and invalid narrowing.

Do not suppress TypeScript errors instead of fixing them.

For substantial edits, running typecheck early after the first
implementation pass is encouraged because it can expose accidental
duplicate edits quickly.

## 17. Validation Order

For meaningful code changes, use this general validation sequence:

1.  Review the final edited files manually.
2.  Run TypeScript typecheck.
3.  Run focused tests for the feature being changed.
4.  Run the full test suite.
5.  Run the server production build and web production build when
    relevant.
6.  Perform the final Git diff audit.

Do not report the task as complete if required validation is failing. If
something cannot be validated, explicitly report what was not validated
and why.

## 18. Large or Multi-File Changes

For large tasks, do not blindly make additive changes across many files.

Work systematically:

``` text
Understand
    ↓
Search
    ↓
Identify existing implementation
    ↓
Modify/replace
    ↓
Review resulting file
    ↓
Typecheck
    ↓
Test
    ↓
Review final diff
```

After modifying one subsystem, verify it before layering additional
changes on top. When multiple files implement the same concept, identify
the canonical abstraction first.

## 19. Repository Hygiene

Do not commit temporary files, generated debug files, editor artifacts,
OS metadata files, `.DS_Store`, AppleDouble `._*` files, credentials,
API keys, local environment secrets, or unnecessary generated output.

Respect existing `.gitignore` rules. Do not modify generated artifacts
unless the task specifically requires it.

## 20. Definition of Done

A coding task is not complete merely because new code was added.

It is complete when:

-   the requested behavior works;
-   the old conflicting implementation is removed;
-   there is one coherent implementation;
-   architectural invariants are preserved;
-   errors are handled appropriately;
-   relevant regression tests exist;
-   typecheck passes;
-   required tests pass;
-   relevant builds pass;
-   modified files have been reread;
-   the final diff has been audited;
-   no duplicate or unreachable implementation remains.

The final codebase should look as though the correct implementation had
been written once, rather than as though multiple patches were stacked
on top of each other.
